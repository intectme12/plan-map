# 운영 배포 계획

> 작성: 2026-09-29 · 상태: **계획(아직 배포 안 함)** — 개발을 더 진행한 뒤 이 문서를 보고 순서대로 준비한다.
> 아키텍처 결정 배경은 [ARCHITECTURE.md](./ARCHITECTURE.md), 실시간 메시지 설계는 [MESSAGING.md](./MESSAGING.md), 인증은 [OAUTH.md](./OAUTH.md) 참고.

이 문서는 "지금 개발용 구성으로는 실서비스에 그대로 못 올리는 부분"과 "어떤 순서로 준비할지"를 정리한다. 요금·리전 목록 같은 외부 서비스 정보는 바뀔 수 있으니 **실제 진행 시점에 각 서비스 공식 문서로 다시 확인**할 것.

## 1. 현재 상태 (2026-09-29 기준)

| 항목 | 지금 | 운영에서 문제 되는 점 |
| --- | --- | --- |
| 앱 실행 | 로컬 `npm run dev`(개발 모드) 하나뿐. 배포 설정 없음(`vercel.json`·`Dockerfile`·CI 전부 없음) | 개발 모드는 페이지 첫 방문마다 컴파일해서 느림 — 운영은 `next build` + `next start` |
| DB | Neon 무료 플랜, **싱가포르(ap-southeast-1)** 리전. 로컬 개발 서버가 이 DB에 직접 연결 | 한국↔싱가포르 왕복 지연, 무료 플랜 절전(콜드 스타트). **개발·검증용 데이터와 섞여 있음** |
| 업로드 파일 | 서버 디스크 `apps/web/public/uploads/`(프로필·여행 사진·메시지 이미지) | 서버리스/다중 서버에선 파일이 사라지거나 서버마다 달라짐, 백업 없음 |
| 실시간 메시지 | SSE + **프로세스 메모리** 구독 목록(`lib/messageEvents.ts`) | 서버가 2대 이상이면 다른 서버에 붙은 사용자에게 알림이 안 감. 서버리스는 긴 연결 유지 자체가 제약 |
| 요청 제한 | 없음(rate limit 미구현) | 로그인 무차별 대입, AI 파싱(Groq 유료 호출) 남용에 무방비 |
| 마이그레이션 | 히스토리 드리프트(`20260907120000_add_trip_visibility_and_shares`) 때문에 스키마 변경마다 수동 우회 중(README "다음 세션 할 일") | 운영 DB를 새로 만들 때 `migrate deploy`가 깔끔히 돌아야 함 |
| 비밀 키 | `.env`(gitignore). 과거 카카오 키가 공개 커밋된 적 있음(README Phase 0) | 유출된 키 재발급 필요, 배포 환경 변수로 관리 |
| 계정 탈퇴 | 없음(사용자 결정으로 별도 작업 예정) | 개인정보 관련 법령상 탈퇴 수단 제공이 필요 — **오픈 전 필수** |

### 측정값 (이 PC → Neon 싱가포르, 2026-09-29)

| 측정 | 결과 |
| --- | --- |
| 절전 상태에서 첫 쿼리 | 약 1,460ms |
| `SELECT 1` 왕복 | 중앙값 약 78ms |
| 여행 목록 쿼리 1개 | 약 360ms |
| 쿼리 5개 순차 | 약 500ms |

→ 느린 주원인은 "무료라서"보다 **거리(쿼리당 ~78ms) × 페이지당 쿼리 수**와 **절전 후 깨어나는 시간**, 그리고 **개발 모드 컴파일**. 핵심 원칙: **앱 서버와 DB를 같은 리전(가능하면 서울)에 둔다** — 사용자↔서버 거리보다 서버↔DB 거리가 체감 속도에 훨씬 크게 작용한다(페이지 하나에 DB 왕복이 여러 번이라).

## 2. 목표 구성 — 두 가지 선택지

### 선택지 A: 서울 리전 서버 1대 (추천 — 첫 오픈용)

```
[사용자] → (도메인/HTTPS) → Node 서버 1대 (서울, next start 상시 실행)
                                 ├─ 페이지 + API
                                 ├─ SSE 실시간 메시지 (메모리 pub/sub 그대로 사용 가능)
                                 ↓
                         관리형 PostgreSQL (서울)      오브젝트 스토리지 (S3/R2 등)
```

- 예: AWS Lightsail/EC2(서울) + RDS(서울), 또는 서울 리전이 있는 관리형 Postgres(Supabase 등)
- **장점**: 지금 구조(SSE 메모리 pub/sub)를 거의 그대로 쓸 수 있음 — 서버가 1대라 문제없음. 가장 적은 코드 변경으로 오픈 가능
- **단점**: 서버 관리(OS 업데이트, 재시작, HTTPS 인증서)를 직접 해야 함. 트래픽이 커져 서버를 늘리려면 그때 Redis 도입 필요
- 업로드 파일은 이 구성에서도 **오브젝트 스토리지로 옮기는 걸 권장**(서버 교체·장애 시 파일 유실 방지, 백업 용이)

### 선택지 B: Vercel(서버리스) + 관리형 DB

```
[사용자] → Vercel (함수 리전: 서울 icn1)
                ↓
        관리형 PostgreSQL (서울 또는 최대한 가까운 리전)   오브젝트 스토리지   Redis/실시간 서비스
```

- **장점**: 배포·HTTPS·확장이 자동. Git push로 배포
- **단점(선행 작업 필수)**:
  - 업로드: 함수 실행 중 디스크에 쓴 파일은 유지·서빙되지 않음 → **오브젝트 스토리지 이전이 필수**
  - 실시간: 함수는 여러 인스턴스로 뜨고 실행 시간 제한이 있어 SSE + 메모리 pub/sub이 그대로는 동작 안 함 → Redis pub/sub이나 관리형 실시간 서비스(Pusher/Ably/Supabase Realtime 등)로 교체 필요
  - DB 연결: 서버리스는 연결이 폭증하기 쉬워 **풀링 주소(pooler) 사용 필수**

### DB 리전 메모

- 현재 Neon 인스턴스는 싱가포르. (작성 시점 지식 기준) Neon은 서울 리전이 없을 수 있으니 **진행 시점에 리전 목록 확인** — 없으면 서울 리전이 있는 서비스(Supabase, AWS RDS/Aurora 등)로 옮긴다. 모두 PostgreSQL이라 Prisma 스키마·코드는 그대로.
- 어떤 서비스든 **운영 DB는 새로 만들고** `prisma migrate deploy`로 스키마만 올린다(지금 Neon의 개발·검증 데이터를 운영으로 가져가지 않음).

## 3. 단계별 체크리스트

### 단계 0 — 개발하면서 미리 해두면 좋은 것 (비용 없음)

- [x] **쿼리 최적화 1차**(2026-09-29 완료): 세션 쿠키 캐시, 헤더 메시지 배지를 가벼운 쿼리로, 여행 상세·공유 페이지 병렬 조회 + 조회 기록 `after()`로 지연, 안읽음 개수 쿼리 1번으로 묶기, Prisma `relationJoins` — 주요 페이지 응답 약 40~65% 단축(README 진행 상황 참고). 이후 새 페이지를 만들 때도 같은 원칙(순차 대기 금지, 반복 쿼리 금지) 유지
- [ ] **마이그레이션 드리프트 해결**: 원인 마이그레이션을 적용 시점 그대로 복원(체크섬 재계산)하거나 베이스라인 마이그레이션으로 정리 → 빈 DB에 `migrate deploy`가 한 번에 성공하는지 확인
- [ ] **개발 DB 분리**: 운영 시작 전에 개발용 DB를 따로 둔다(Neon 브랜치 기능 또는 별도 인스턴스). 검증용 임시 계정 생성·삭제는 개발 DB에서만
- [ ] **Prisma 연결 주소 분리**: `schema.prisma`에 `directUrl` 추가 — 앱은 풀링 주소(`DATABASE_URL`), 마이그레이션은 직접 연결 주소(`DIRECT_URL`)
- [ ] **계정 탈퇴 기능** 구현(별도 작업으로 예정) — 여행·사진·메시지·공유·팔로우 데이터 처리 정책 먼저 결정
- [ ] **업로드 저장 추상화**: `lib/upload.ts`의 `saveImageFile`/`deleteStoredFile`만 바꾸면 되도록 저장소 교체 지점을 한곳으로 유지(이미 한곳에 모여 있음 — 호출부가 늘어나지 않게 주의)

### 단계 1 — 배포 준비 (코드 변경)

- [ ] **업로드 파일 → 오브젝트 스토리지(S3/Cloudflare R2 등)**
  - `lib/upload.ts` 교체: 저장 경로 대신 스토리지 키/URL을 `storageKey`로 저장
  - 기존 `/uploads/...` 형식 데이터 이전 스크립트(파일 업로드 + DB 값 치환)
  - 이미지 제공은 CDN 주소로, 필요하면 `next.config.ts`의 `images.remotePatterns` 설정
- [ ] **실시간 메시지** (선택지 B이거나 서버를 2대 이상 둘 때만 필수)
  - `lib/messageEvents.ts`의 메모리 구독 목록 → Redis pub/sub(또는 관리형 실시간 서비스)
  - 구독/발행 함수 시그니처는 유지해서 호출부(`conversations.ts`, `/api/messages/stream`) 변경 최소화
- [ ] **요청 제한(rate limit)**: 로그인·회원가입, AI 파싱(`/api/trips/[id]/ai-parse` — Groq 비용), 메시지 전송, 업로드에 우선 적용
- [ ] **보안 헤더**: `next.config.ts`에 기본 보안 헤더(CSP는 카카오맵 SDK 도메인 허용 필요), 쿠키 `Secure` 확인
- [ ] **오류 처리 점검**: 운영에서 `console.error`만으로는 추적 불가 → 오류 수집 도구 연결 준비(단계 2)

### 단계 2 — 인프라 구성

- [ ] 도메인 구입 + DNS 설정 + HTTPS
- [ ] 운영 DB 생성(서울 리전), 자동 백업·특정 시점 복구(PITR) 켜기, 절전(자동 일시정지) 끄기 또는 최소화
- [ ] 오브젝트 스토리지 버킷 생성 + CDN
- [ ] 앱 서버(선택지 A) 또는 Vercel 프로젝트(선택지 B, 함수 리전 서울) 구성
- [ ] **환경 변수 설정**(아래 4장 목록)
- [ ] 첫 배포 전: 운영 DB에 `npx prisma migrate deploy`
- [ ] 스테이징 환경(운영과 같은 구성의 작은 사본)에서 한 번 전체 점검

### 단계 3 — 외부 서비스 설정

- [ ] **카카오 개발자 콘솔**: 플랫폼 > Web 사이트 도메인에 운영 도메인 추가(JS SDK 지도 표시 조건), 카카오 로그인 Redirect URI 추가
- [ ] **네이버·구글 콘솔**: OAuth 리디렉션 URI 추가 — 형식 `{BETTER_AUTH_URL}/api/auth/callback/{provider}`
- [ ] **유출됐던 카카오 키 재발급** 후 새 키만 사용(README Phase 0 잔여 작업)
- [ ] Groq API: 운영 키 발급, 사용량 한도/알림 설정
- [ ] 카카오모빌리티 경로 API가 운영 서버에서 실제 값(거리·시간·택시요금)을 돌려주는지 확인 — 로컬에선 인증서 가로채기 문제로 끝까지 검증 못 함(README 참고)

### 단계 4 — 오픈 직전

- [ ] **법적 고지**: 개인정보 처리방침, 이용약관 페이지 — 회원가입 시 동의 흐름. 수집 항목(이메일, 닉네임, 프로필 사진, 여행·위치 정보가 담긴 장소 데이터, 메시지)과 보관·파기 기준 명시. 위치 관련 법적 요건 해당 여부는 전문가 확인 권장
- [ ] 계정 탈퇴 동작 확인(단계 0)
- [ ] 모니터링: 오류 수집(예: Sentry), 서버·DB 지표(CPU·연결 수·느린 쿼리), 가동 확인(uptime) 알림
- [ ] 백업 복구 리허설: 백업에서 실제로 되살릴 수 있는지 한 번 확인
- [ ] 운영 빌드로 전체 기능 점검: 회원가입/로그인(이메일·소셜 3종), 여행 생성·수정·공유, 사진 업로드, 메시지 실시간 수신, AI 일정 생성, 지도/경로

### 단계 5 — 오픈 후

- [ ] 느린 페이지·쿼리 확인 후 인덱스·쿼리 개선
- [ ] 트래픽 증가 시: 서버 증설(선택지 A면 이때 Redis 도입), DB 사양 상향, 읽기 전용 복제본 검토
- [ ] 주기 점검: 의존성 보안 업데이트, 비밀 키 교체, 백업 상태

## 4. 운영 환경 변수

`apps/web/.env.example` 기준. 운영 값은 배포 플랫폼의 환경 변수/비밀 저장소에만 둔다(파일 커밋 금지).

| 변수 | 운영에서 주의할 점 |
| --- | --- |
| `DATABASE_URL` | 운영 DB의 **풀링 주소** |
| `DIRECT_URL` | (단계 0에서 추가 예정) 마이그레이션용 직접 연결 주소 |
| `BETTER_AUTH_SECRET` | 새로 생성한 긴 랜덤 값 — 개발 값 재사용 금지 |
| `BETTER_AUTH_URL` | 운영 도메인(`https://...`) — OAuth 리디렉션 URI의 기준 |
| `NEXT_PUBLIC_KAKAO_JS_KEY` | 브라우저에 노출되는 키 — 카카오 콘솔에서 운영 도메인만 허용 |
| `KAKAO_REST_API_KEY` | 서버 전용, 재발급한 새 키 |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | 운영용 OAuth 앱 |
| `KAKAO_CLIENT_ID` / `KAKAO_CLIENT_SECRET` | 〃 (이메일 동의항목은 사업자 인증 필요 — 미인증 시 코드가 대체 이메일 처리) |
| `NAVER_CLIENT_ID` / `NAVER_CLIENT_SECRET` | 〃 |
| `GROQ_API_KEY` | 운영 키 + 사용량 한도 |
| (추가 예정) 스토리지 키·버킷명, Redis 주소, 오류 수집 DSN | 단계 1~2에서 추가 |

## 5. 추천 진행 순서 요약

1. **개발 기간 중**: 단계 0(쿼리 최적화, 마이그레이션 정리, 개발 DB 분리, `directUrl`, 계정 탈퇴)
2. **오픈 1~2주 전**: 단계 1(스토리지 이전, rate limit, 보안 헤더) → 단계 2~3(서울 리전 인프라, 외부 콘솔 설정)
3. **오픈 직전**: 단계 4(법적 고지, 모니터링, 백업 리허설, 전체 점검)
4. 첫 오픈은 **선택지 A(서울 서버 1대)** 로 가볍게 시작하고, 트래픽이 늘면 Redis 도입 후 서버를 늘리거나 선택지 B로 옮기는 것을 검토
