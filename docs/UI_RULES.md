# UI / UX 규칙

> 네비게이션, 반응형/모바일 동작, 접근성, 폼, 상태(로딩/빈 상태/오류/성공), 피드백, 테이블, 오버레이, 성능, UX 라이팅, 보안을 고려한 UI, 다국어 대응, 최종 페이지 검수 기준 등 동작·인터랙션·UX 품질을 위한 실전 체크리스트. 프로젝트 도메인과 무관하게 범용적으로 쓸 수 있어 plan-map에도 그대로 적용한다.
>
> 시각적 토큰/컴포넌트는 [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md), AI 코딩 에이전트에게 지시할 때의 규칙은 [AI_CODING_RULES.md](AI_CODING_RULES.md) 참고.

---

# 1. 네비게이션

- [ ] 사용자가 현재 어느 화면에 있는지 알 수 있어야 한다.
- [ ] 현재 활성화된 메뉴를 명확하게 표시한다.
- [ ] 메뉴 이름은 짧고 직관적으로 작성한다.
- [ ] 지나치게 깊은 메뉴 구조를 피한다.
- [ ] 페이지가 바뀌어도 네비게이션 동작을 일관되게 유지한다.
- [ ] 모바일 네비게이션은 데스크톱의 단순 축소판으로 만들지 않는다.

---

# 2. 반응형 디자인

데스크톱만 기준으로 디자인하지 않는다. 최소한 다음 환경을 테스트한다.

- [ ] Desktop
- [ ] Laptop
- [ ] Tablet
- [ ] Mobile
- [ ] Small mobile

Breakpoint는 특정 기기 이름보다 실제 레이아웃이 깨지는 지점을 기준으로 정한다.

확인:

- [ ] 텍스트 줄바꿈
- [ ] 버튼 너비
- [ ] 네비게이션 축소
- [ ] 테이블 overflow

---

# 3. 접근성

접근성은 선택 기능이 아니라 좋은 UX의 기본 요소다.

- [ ] 시맨틱 HTML을 사용한다.
- [ ] 모든 인터랙션 요소는 키보드로 조작할 수 있어야 한다.
- [ ] focus 상태를 명확하게 표시한다.
- [ ] 이미지에 적절한 alt 텍스트를 제공한다.
- [ ] 폼 입력에는 label을 제공한다.
- [ ] 상태를 색상만으로 전달하지 않는다.
- [ ] 충분한 색상 대비를 유지한다.
- [ ] Dialog와 Drawer의 focus 이동을 올바르게 처리한다.

---

# 4. 폼과 사용자 입력

폼은 UX 품질을 크게 좌우하는 영역이다.

- [ ] Label은 입력 항목의 의미를 명확하게 설명한다.
- [ ] Placeholder를 Label 대신 사용하지 않는다.
- [ ] 이메일, 숫자, 날짜 등 적절한 input type을 사용한다.
- [ ] 적절한 시점에 validation을 수행한다.
- [ ] 오류 메시지는 해당 입력창 근처에 표시한다.
- [ ] 오류가 발생한 이유뿐 아니라 해결 방법도 알려준다.
- [ ] validation 오류가 발생해도 사용자가 입력한 값을 유지한다.
- [ ] 명확한 이유가 없다면 submit 버튼을 무조건 disabled 처리하지 않는다.

좋은 오류 메시지: "비밀번호는 최소 8자 이상이어야 합니다." — 나쁜 예: "잘못된 입력입니다."

---

# 5. 로딩 / 빈 상태 / 오류 / 성공 상태

정상적인 데이터가 존재하는 상황만 디자인하지 않는다. 모든 주요 화면에서 다음 상태를 고려한다: 로딩, 빈 상태, 성공, 오류, 부분 데이터, 권한 없음, 오프라인.

## 로딩

- [ ] 콘텐츠가 많은 화면에는 적절한 경우 Skeleton을 사용한다.
- [ ] 짧은 작업에 불필요한 Spinner를 사용하지 않는다.
- [ ] 로딩 전후 레이아웃이 크게 움직이지 않도록 한다.

## 빈 상태

좋은 Empty State는 다음을 설명한다: 1) 현재 상태가 무엇인지 2) 왜 비어 있는지 3) 사용자가 무엇을 할 수 있는지.

## 오류 상태

- [ ] 무엇이 잘못되었는지 설명한다.
- [ ] 재시도 등의 복구 액션을 제공한다.
- [ ] 일반 사용자에게 기술적인 에러 메시지를 그대로 보여주지 않는다.

---

# 6. 사용자 피드백과 인터랙션

사용자의 행동에는 이해 가능한 피드백이 따라야 한다. 예: 클릭 → 시각적 반응, Submit → 로딩, 성공 → toast/인라인 확인, 오류 → 명확한 오류 메시지, 삭제 → 위험한 작업이면 확인, 저장 → 저장됨 표시.

- [ ] 버튼은 interaction에 시각적으로 반응한다.
- [ ] 오래 걸리는 작업은 진행 상태를 보여준다.
- [ ] 삭제 같은 위험한 작업은 적절한 확인 절차를 제공한다.
- [ ] Toast는 짧고 필요한 정보만 전달한다.

---

# 7. 테이블과 데이터 중심 화면

관리자/데이터 중심 화면에서는 테이블 UX가 매우 중요하다.

- [ ] 헤더와 데이터를 명확하게 구분한다.
- [ ] 숫자 데이터를 일관되게 정렬한다.
- [ ] 컬럼 너비를 읽기 쉽게 설정한다.
- [ ] 필요한 경우 정렬 기능을 제공한다.
- [ ] 데이터가 많다면 필터 기능을 제공한다.
- [ ] 대량 데이터에는 pagination 또는 virtualization을 사용한다.
- [ ] 가로 스크롤이 필요한 경우 의도적으로 설계한다.
- [ ] 주요 액션을 쉽게 찾을 수 있도록 한다.

---

# 8. 모달 / Drawer / Overlay

집중된 작업을 처리하는 데 도움이 되는 경우에만 Overlay를 사용한다.

- [ ] 전체 업무 흐름을 거대한 모달 안에 넣지 않는다.
- [ ] 현재 화면의 맥락을 유지한 채 수정할 때 Drawer를 고려한다.
- [ ] 닫기 동작을 예측 가능하게 만든다.
- [ ] Escape 키 동작을 처리한다.
- [ ] focus 이동을 올바르게 관리한다.

---

# 9. 성능을 고려한 디자인

디자인 결정은 성능에 직접적인 영향을 줄 수 있다.

- [ ] 불필요하게 큰 이미지를 사용하지 않는다.
- [ ] 과도한 blur/backdrop-filter를 사용하지 않는다.
- [ ] 수백 개의 요소를 동시에 애니메이션하지 않는다.
- [ ] 필요한 경우 화면 아래쪽 콘텐츠를 lazy loading한다.
- [ ] 매우 큰 리스트는 virtualization을 고려한다.
- [ ] 사용하지 않는 무거운 컴포넌트를 불필요하게 렌더링하지 않는다.

---

# 10. 모바일 UX

모바일은 데스크톱을 작게 만든 것이 아니다.

- [ ] 가장 중요한 액션을 우선 배치한다.
- [ ] 충분한 터치 영역을 제공한다.
- [ ] 너무 작은 텍스트를 사용하지 않는다.
- [ ] 데이터 테이블 등 필요한 경우를 제외하고 가로 스크롤을 피한다.
- [ ] 한 손 사용을 고려한다.
- [ ] 중요한 액션은 손가락이 닿기 쉬운 위치에 배치한다.

---

# 11. UX 라이팅

UI 문구도 디자인의 일부다.

- [ ] 짧고 명확한 라벨을 사용한다.
- [ ] 동일한 기능에는 동일한 용어를 사용한다.
- [ ] 불필요한 기술 용어를 사용하지 않는다.
- [ ] 사용자가 다음 행동을 알 수 있는 오류 메시지를 작성한다.
- [ ] 버튼 이름은 행동을 나타내도록 작성한다.

선호: "프로젝트 생성" — 비추천: "확인"

---

# 12. 보안을 고려한 UI

프론트엔드 디자인에서도 보안과 관련된 사용자 경험을 고려해야 한다.

- [ ] 민감한 작업을 명확하게 구분한다.
- [ ] 삭제/탈퇴 등의 위험한 작업은 적절하게 확인한다.
- [ ] API Key, Token, Password 등의 민감 정보를 불필요하게 표시하지 않는다.
- [ ] 필요한 경우 민감한 값을 마스킹한다.
- [ ] 권한 오류를 명확하게 설명한다.
- [ ] 백엔드 구현 정보를 사용자 화면에 그대로 노출하지 않는다.

---

# 13. 다국어와 한글 UX

향후 다국어를 지원할 가능성이 있다면 처음부터 확장성을 고려한다.

- [ ] 특정 문구의 길이를 기준으로 레이아웃을 고정하지 않는다.
- [ ] 영어/한국어 등으로 변경되었을 때 텍스트가 길어지는 상황을 고려한다.
- [ ] 한글과 영어 화면을 각각 테스트한다.
- [ ] 날짜, 숫자, 통화 표시 형식을 확인한다.
- [ ] 특정 언어에서만 버튼 크기가 맞는 구조를 피한다.

---

# 14. 브라우저와 디바이스 테스트

최소한 다음 환경을 확인한다: Chrome, Safari, Edge, Desktop, Mobile browser, 다양한 뷰포트 너비, High-DPI 디스플레이.

확인 항목: 레이아웃, 폰트 렌더링, Sticky 요소, 스크롤, Fixed positioning, 모달 동작, 키보드 동작, 터치 동작.

---

# 15. 페이지별 최종 검수 체크리스트

페이지를 완료 처리하기 전에 확인한다.

- [ ] 페이지의 목적이 즉시 이해되는가?
- [ ] 핵심 액션이 명확한가?
- [ ] 시각적 계층이 명확한가?
- [ ] 간격과 typography가 일관적인가?
- [ ] 공통 컴포넌트가 올바르게 재사용되었는가?
- [ ] 로딩 상태가 구현되어 있는가?
- [ ] 빈 상태가 구현되어 있는가?
- [ ] 오류 상태가 구현되어 있는가?
- [ ] 성공 상태가 구현되어 있는가?
- [ ] 반응형으로 동작하는가?
- [ ] 키보드로 사용할 수 있는가?
- [ ] 색상 대비가 충분한가?
- [ ] 모바일 터치 영역이 충분한가?
- [ ] 긴 텍스트가 들어와도 깨지지 않는가?
- [ ] 데이터가 없거나 매우 많아도 정상적으로 동작하는가?
- [ ] 삭제 등의 위험한 액션이 적절하게 보호되는가?
- [ ] 기존 디자인 시스템을 따르는가? ([DESIGN_SYSTEM.md](DESIGN_SYSTEM.md) 참고)

---

# 16. 최종 디자인 품질 기준

페이지가 기능적으로 동작한다고 해서 완성된 것이 아니다. 다음 5단계를 모두 통과해야 한다.

### Gate 1 — 일관성

같은 제품의 화면처럼 보이는가?

### Gate 2 — 명확성

사용자가 무엇을 해야 하는지 쉽게 알 수 있는가?

### Gate 3 — 피드백

중요한 행동에 적절한 피드백이 제공되는가?

### Gate 4 — 예외 대응

로딩, 빈 상태, 오류, 긴 텍스트, 대량 데이터에서도 정상적으로 보이는가?

### Gate 5 — 접근성

다양한 사용자가 불편 없이 사용할 수 있는가?

---

# 17. 핵심 원칙

1. **새로움보다 일관성이 중요하다.**
2. **장식보다 명확성이 중요하다.**
3. **복잡한 UI보다 명확한 정보 계층이 중요하다.**
4. **반복 구현보다 재사용이 중요하다.**
5. **사용자 행동에는 반드시 적절한 피드백이 있어야 한다.**
6. **모바일은 부가 기능이 아니라 독립적인 UX로 취급한다.**
7. **접근성은 품질의 일부다.**
8. **정상 상태뿐 아니라 예외 상태까지 디자인한다.**
9. **예쁘지만 사용하기 어려운 UI는 좋은 디자인이 아니다.**

---

# 결론

좋은 웹 디자인 시스템의 목표는 모든 화면을 화려하게 만드는 것이 아니다. 전체 애플리케이션이 **일관되고, 예측 가능하며, 명확하고, 빠르고, 접근 가능하고, 신뢰감 있게** 느껴지도록 만드는 것이 목표다.
